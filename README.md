# Slack-MM2 Sync

Моно-репозиторий для приложения односторонней синхронизации данных Slack с Mattermost.

## Структура проекта

- `backend/` — Python FastAPI backend, реализующий API, обработку загрузки файлов и webhook.
- `frontend/` — React frontend, UI для загрузки файлов и мониторинга статуса.
  - Dev режим: исходники монтируются read-only; зависимости устанавливаются в эфемерную рабочую директорию контейнера при каждом старте (см. `frontend/README.md`).
- `infra/` — инфраструктура, манифесты Kubernetes, документация по деплою и настройке.

## Быстрый старт
Ниже краткий маршрут для локального dev-окружения (детали см. `backend/README.md`, `frontend/README.md`, `infra/README.md`).

1. Установите зависимости локально (опционально, для разработки вне Docker):
  ```bash
  pip install -r backend/requirements.txt
  npm -C frontend ci
  ```
2. Создайте `.env` для dev (токены фиктивны, используются только локально):
  ```bash
  cat > infra/.env <<EOF
  SLACK_VERIFICATION_TOKEN=test_token
  SLACK_BOT_TOKEN=test_bot_token
  SLACK_SIGNING_SECRET=test_signing_secret
  EOF
  ```
3. Поднимите всё окружение (всегда полный стек, без выборочного включения сервисов):
  ```bash
  docker compose -f infra/docker-compose.dev.yml up --build -d
  ```
4. Проверьте точки входа:
  - Backend: http://localhost:8000/healthcheck
  - Frontend: http://localhost:5173
  - Mattermost: http://localhost:8065
  - Test files (локальные вложения): http://localhost:9000
5. Загрузите тестовый архив Slack через UI или CLI: `curl -F file=@infra/test-data/slack-mini-backup.zip http://localhost:8000/upload`

### Мини-интеграционный прогон

Скрипт `scripts/run_mini_backup_integration.sh` выполняет детерминированную полную проверку импорта/экспорта на мини-наборе данных:
```
./scripts/run_mini_backup_integration.sh
```
Он гарантированно:
 - Поднимает полный docker-compose стек.
 - Убеждается в деплое/включении плагина Mattermost Importer.
 - Загружает мини-архив (`infra/test-data/slack-mini-backup.zip`).
 - Поллит `/jobs` до статуса success и проверяет итоговые счётчики.
 - Сканирует backend логи на ошибки и валидирует связывание admin пользователя.
 - Корректно гасит стек (даже при ошибке).

Используйте его локально и в CI для быстрой регрессии. Любые изменения структуры данных мини-набора должны сопровождаться обновлением ожидаемых метрик в самом скрипте.

### Правила (policy) mini-backup архива

`infra/test-data/slack-mini-backup.zip` — канонический минимальный набор для детерминированной регрессии. Любое отклонение от него должно быть осознанным и отражено в этом README и в `scripts/run_mini_backup_integration.sh`.

Основные правила:
1. Источник истины — ZIP. Распакованная папка может храниться, но её содержимое обязано побайтно соответствовать архиву.
2. Плоская структура внутри архива (нет корневой обёрточной директории). Файлы верхнего уровня: `users.json`, `channels.json`, `groups.json` (если есть), `dms.json`, каталоги каналов/DM c файлами дат.
3. Изменение содержимого -> обязательно:
  - Перегенерировать архив: `python infra/test-data/build_mini_backup_zip.py`
  - Обновить ожидаемые счётчики в `scripts/run_mini_backup_integration.sh`
  - Обновить раздел «Мини-набор (эталон)» и этот раздел.
4. Никаких временных правок для отладки: используйте отдельный архив вне репозитория.
5. `url_private` файлов должны начинаться с одного из `IMPORT_URL_PREFIXES` (по умолчанию: `https://files.slack.com,http://test-files:9000`) — иначе вложение будет отфильтровано и нарушит счётчик.
6. Текущие эталонные значения (финальные totals): users=3, channels=3, messages=17, attachments=3, reactions=1.
7. Добавление нового типа сущности / счётчика в mini-backup делается только вместе с обновлением тестов, README и интеграционного скрипта (ранний успех не должен ломаться).
8. Контент детерминирован: никаких timestamp-зависимых генераций. Пересборка архива без правок даёт идентичный файл (исключая метаданные zip уровня времени модификации — это допустимо).

Checklist обновления mini-backup:
1. Правим файлы в распакованной `infra/test-data/slack-mini-backup/`.
2. Генерируем: `python infra/test-data/build_mini_backup_zip.py`.
3. Запускаем: `./scripts/run_mini_backup_integration.sh` — убеждаемся в раннем успехе.
4. Обновляем README + скрипт + коммитим zip.
5. Ждём зелёный CI.

### Политика дубликатов ("dup variants") DM / channel сообщений

В мини-наборе существуют варианты сообщений, которые потенциально могли бы рассматриваться как «дубликаты» (одинаковый текст / близкие временные метки в том же DM/канале). **Политика канонического импорта**: мы НЕ выполняем дедупликацию и **засчитываем каждое сообщение, имеющее валидный `ts`**, независимо от совпадений содержимого. Причины:

1. Детерминизм: отсутствие эвристик дедупликации исключает дрейф счётчиков при изменении алгоритма или добавлении новых типов сообщений.
2. Прозрачность: «сырой» Slack экспорт трактуется как источник истины; любое смещение чисел требует явного изменения данных, а не кода.
3. Тестовая устойчивость: регрессия фокусируется на точности парсинга и атомарности счётчиков, а не на бизнес-логике очистки.

Следствие: если в будущем понадобится слой дедупликации, он будет реализован как отдельная пост‑обработка, НЕ влияющая на канонические baseline‑счётчики mini-backup. На момент текущей версии baseline (users=3, channels=3, messages=17, attachments=3, reactions=1) — все 17 сообщений учитывают «dup variants».

### Тротблшутинг healthcheck backend (при зависании интеграционного скрипта)

Симптом: многократные строки `[WAIT] health attempt=N code=000 body={"status":"ok"}` и отсутствие перехода к шагу загрузки архива.

Что означает `code=000` здесь — `curl` не смог установить соединение (порт не слушает или временный отказ), при этом файл `/tmp/health.json` мог содержать результат предыдущей удачной попытки, поэтому body может выглядеть "здоровым".

Вероятные причины:
1. Миграции ещё выполняются (алембик запускается в lifespan до старта uvicorn).
2. Подключение к Mattermost внутри авто-ensure плагина (сетевые таймауты) замедляет старт.
3. Порт 8000 занят другим локальным процессом.
4. Ошибка миграции / исключение в lifespan — uvicorn не поднялся.

Диагностика:
```bash
docker compose -f infra/docker-compose.dev.yml logs -n 200 backend
docker compose -f infra/docker-compose.dev.yml ps
curl -v http://localhost:8000/healthcheck || true
ss -tnlp | grep :8000 || true
```

Оптимизации скрипта (внесены): перед каждой попыткой health файл обнуляется, добавлены таймауты `--connect-timeout` и `--max-time` — предотвращает reuse устаревшего body.

Потенциальные улучшения (roadmap): вынести ensure плагина в отложенную фон.задачу после старта сервера, чтобы healthcheck проходил быстрее; добавить ранний вывод логов после N неудачных попыток.


## Архитектура импорта (унифицированный однопроходный пайплайн)

Импорт Slack → Mattermost реализован как ЧЁТКО ДЕТЕРМИНИРОВАННЫЙ, однонаправленный, однопроходный конвейер стадий:

1. `extracting` – загрузка и первичная проверка архива (требование: «плоская» структура, без обёрточной директории).
2. `users` – разбор и импорт пользователей.
3. `channels` – разбор и импорт каналов / DM / групповых DM.
4. `messages` – единый проход по сообщениям КАЖДОГО канала, в рамках КОТОРОГО одновременно импортируются:
  - сами сообщения,
  - реакции,
  - вложения (attachments / files),
  - упоминания кастомных emoji (для последующего экспорта их определения),
  - связи (entity relations).
5. `exporting` – единая фазa экспорта уже полностью собранных данных в Mattermost (через плагин или API вызовы).
6. `done` – окончательный терминальный статус.

Отсутствуют любые многошаговые/многоцикловые «догоночные» этапы для реакций, вложений и пр. Всё фиксируется в одном проходе сообщений, что:
* устраняет условия гонок по счётчикам,
* упрощает reasoning о прогрессе,
* гарантирует репродуцируемость результатов (одно и то же число сообщений / вложений на одних и тех же данных).

## Детерминированные счётчики прогресса

Все счётчики прогресса монотонно неубывающие: НИКОГДА не «откатываются» назад при смене стадии. Обновление реализовано атомарной SQL функцией слияния JSONB (см. ниже). Основные ключи `meta`:

| Ключ meta | Значение |
|-----------|----------|
| `users_processed` | Кол-во импортированных пользователей |
| `channels_processed` | Кол-во импортированных каналов (вкл. DM/группы) |
| `messages_processed` | Кол-во импортированных сообщений |
| `reactions_processed` | Кол-во реакций |
| `attachments_processed` | Кол-во файлов / вложений |
| `emojis_processed` | Кол-во уникальных упомянутых custom emoji (если применимо) |
| `totals`.* | Итоговые значения, зафиксированные при переходе в `exporting` / `done` (консолидация) |
| `durations_ms`.* | (Опционально) длительности стадий, если включено профилирование |
| `totals_frozen` | true после консолидации (в стадии exporting/done); denominator стабилен |

Мини-набор (эталон для регрессии) — ожидаемые финальные значения:

```
users=3
channels=3
messages=17
attachments=3
reactions=1
```

При запуске мини-интеграции финальные цифры появляются уже на раннем POLL (обычно второй опрос) в стадии `exporting` — это считается «ранним успехом» (см. ниже).

Инварианты:
* Ни один *_processed счётчик не уменьшается.
* При входе в `exporting` выполняется консолидация: в `totals` записываются зафиксированные финальные значения.
* Эндпоинт `/jobs` для стадий `exporting` и `done` всегда возвращает максимум из текущего meta и зафиксированного totals, исключая визуальные регрессии.

## Atomic merge метаданных (`merge_job_meta`)

Историческая проблема: потеря инкрементов (lost update) из‑за смешанных ORM read‑modify‑write и независимых UPDATE по JSONB. Решение — единый SQL UPDATE с атомарным слиянием полей `meta`.

Поддерживаемые операции (конструируются динамически):
* `incr` – атомарное увеличение числовых полей (`*_processed`).
* `set` – установка значения (стадия, служебные флаги и т.п.).
* `max` – монотонное взятие максимума (используется для гарантии неубывающих счётчиков даже при условной гонке).
* `nested` – слияние вложенных JSON-объектов (например, `durations_ms`, `totals`).
* `remove` – удаление ключей (используем ограниченно, в основном при очистке временных служебных значений).

Все параметры приводятся к нужным типам явными ::int / ::jsonb кастами → исключено появление `IndeterminateDatatypeError` и «тихих» инвалидных значений. Это гарантия консистентности метаданных при высокой частоте апдейтов.

Инварианты atomic merge:
1. Один SQL round‑trip на группу обновлений.
2. Нет чтения meta до обновления (write-only, оптимистично, без блокирующих SELECT FOR UPDATE).
3. Любая гонка между `incr` и `max` заканчивается корректным числом ≥ каждого из конкурирующих инкрементов.
4. Возврат значения в ответ API отделён от механизма обновления — клиент видит накопленные значения без «скачков вниз».

## Раннее успешное завершение mini-интеграции

Скрипт `run_mini_backup_integration.sh` считает прогон успешным, как только стадия перешла в `exporting` И финальные счётчики совпали с эталоном. Завершения `done` дожидаться не требуется для регрессии мини-набора — экспорт может продолжать побочные операции (например, упаковку), но данные уже полностью идентичны целевым.

Причины подхода:
* Резкое ускорение обратной связи (секунды вместо потенциального ожидания завершающей части экспорта).
* Исключение ложных «зависаний», когда пользователь ожидает роста счётчиков после фактически завершённого импорта.
* Подчёркивание архитектурного факта: вся бизнес-ценность (полный объём данных) готова ещё до окончания финализации.

Если ваш новый код добавляет сущности/счётчики, обновите:
1. Скрипт мини-интеграции (ожидаемые значения).
2. Эту таблицу в README.
3. Локальные/CI тесты, чтобы предотвратить немой дрейф метрик.

## Политика изменений импортера

Любой refactor стадии или добавление новых подсущностей должно сохранять:
* Однопроходную семантику (`messages` остаётся точкой агрегации реакций/вложений/emoji).
* Монотонность и атомарность счётчиков.
* Отсутствие feature‑flags: новая логика сразу активна при мерже.
* Репродуцируемость мини-набора (обновить эталон только при объективном расширении данных, а не из‑за дрейфа).

Перед PR: убедитесь, что мини-интеграционный скрипт завершился ранним успехом, и логи не содержат ERROR.* для бэкенда.

Если изменения затрагивают подсистему подсчёта сообщений или потенциально могут исключать сообщения (например, добавление фильтров по subtype), **обязательно** пересчитать mini-backup вручную и подтвердить, что счётчик messages остаётся равным 17. Любое намеренное изменение baseline требует отдельного PR с явной пометкой "baseline change" в заголовке.

### О сервисе test-files

В dev compose есть сервис `test-files` (порт 9000) — простой HTTP сервер, отдающий содержимое `infra/test-data/`. Мини-набор Slack указывает `url_private` вложений на `http://test-files:9000/...`, что устраняет сетевые задержки и делает проверку быстрой и повторяемой.

Политика: скрипты/документация **никогда** не подразумевают выборочное поднятие сервисов – всегда полный стек для исключения скрытых зависимостей.

## Политика ветвления (Branching Policy)
Все изменения вносятся ТОЛЬКО через отдельные ветки. Запрещено коммитить напрямую в `master`.

Шаги типового потока:
1. Обновить master: `git fetch origin && git checkout master && git pull --rebase`.
2. Создать ветку: `git checkout -b feature/<кратко>` (или `fix/`, `chore/`, `docs/`).
3. Вносить изменения — маленькие логически связанные коммиты, перед пушем запускать форматтеры и тесты.
4. Актуализировать ветку перед PR: `git fetch origin && git rebase origin/master`.
5. Пуш: `git push -u origin feature/<кратко>`.
6. Открыть Pull Request → дождаться CI → ревью → merge (squash или fast-forward).
7. Удалить ветку (локально и в origin).

Жёсткие правила:
- Никаких force push в `master`.
- `master` всегда в рабочем состоянии (тесты зелёные, миграции валидны).
- Хотфикс: `hotfix/<issue>` + PR, даже при срочности.
- Крупные рефакторинги — разбивать на серию PR.

Причины: чище история, меньше конфликтов, предсказуемый CI сигнал, возможность безопасного rebase.

- В сервисе backend не используется volume ../backend:/app, чтобы не перекрывать содержимое, скопированное в образ (особенно миграции). Это гарантирует, что проект работает и в Docker Compose, и при ручном запуске/сборке.

- Пример запуска:

  ```bash
  MATTERMOST_API_TOKEN=... MATTERMOST_API_URL=... pytest backend/tests/integration
  ```

- Для запуска тестов с покрытием: `pytest --cov=app --cov-report=term-missing`

## Pre-commit хуки

Чтобы автоматически проверять стиль и базовые ошибки перед коммитом, добавлен файл `.pre-commit-config.yaml`.

Установка и активация (один раз):
```bash
pip install -r backend/requirements.txt  # содержит pre-commit
pre-commit install
```

Что запускается при `git commit`:
- `black` — автоформатирование Python
- `end-of-file-fixer`, `trailing-whitespace`, `detect-private-key`, `check-added-large-files`
- Опциональный быстрый юнит-тест хук (`pytest-unit-fast`) — можно пропустить: `SKIP=pytest-unit-fast git commit -m "msg"`

Ручной прогон для всего репозитория (рекомендуется после больших refactor):
```bash
pre-commit run --all-files
```

Добавление нового hook:
1. Открыть `.pre-commit-config.yaml`
2. Добавить запись, указать `rev` (фиксированную версию)
3. `pre-commit autoupdate` (по желанию) и закоммитить изменения.

Если CI падает на format step — сначала локально запустить `pre-commit run --all-files` и повторить коммит.

## Запуск тестов: юнит vs интеграционные
- **Юнит-тесты** не требуют запуска внешних сервисов (БД, Mattermost, backend). Их можно запускать где угодно: локально, в CI, без Docker.
- **Интеграционные тесты** требуют, чтобы все внешние сервисы были доступны (backend, Mattermost, БД). Обычно их запускают из-под `docker compose up` или в CI, где все сервисы подняты синхронно.
- Для интеграционных тестов обязательно проверьте, что переменные окружения (`MATTERMOST_API_TOKEN`, `MATTERMOST_API_URL` и др.) указывают на правильные адреса сервисов. 

## Терминология
- **upload** — процесс загрузки файла (например, бэкапа Slack) с фронта на backend.
- **webhook** — приём обновления через вебхук (например, события из Slack в режиме реального времени).
- **parsing** — процедура чтения и разбора полученных данных (как из файла, так и из вебхука).
- **маппинг (mapping)** — одиночная распарсенная строка/объект, представляющая одну сущность (например, сообщение, пользователь, канал и т.д.).
- **импорт (import)** — процедура занесения маппинга в базу данных проекта.
- **экспорт (export)** — процедура отправки данных из маппинга в Mattermost (через API). 

## Политика использования переменных окружения

Мы намеренно минимизируем количество переменных окружения.

Принципы:
1. Только необходимая конфигурация среды: пути к сервисам (URL), токены доступа, размеры таймаутов/пулов соединений, параметры производительности, требуемые для развёртывания в разных окружениях (dev/stage/prod).
2. Никаких feature‑flags через env: функциональность приложения должна вести себя одинаково при одинаковой версии кода. Новые фичи включаются сразу (или за счёт явной логики версии данных / наличия сущностей), а не с помощью скрытых переключателей.
3. Повторяемость CI/Prod: всё, что влияет на ветвление логики, фиксируется в коде или конфигурационных файлах репозитория (migrations, manifests), а не в случайных переменных среды.
4. Допустимые исключения: секреты и параметры, которые невозможно хранить в Git (пароли, токены), а также значения, которые объективно различаются между инсталляциями (доменные имена, внешние URL). Они не должны менять поведение алгоритмов.
5. Если кажется, что нужна новая переменная окружения «чтобы быстро что‑то отключить/включить», сначала переосмысливаем архитектуру (можно ли сделать код идемпотентным / безопасным всегда) или фиксируем поведение через конфиг в репозитории.

Следствие: при ревью любой новой env переменной нужно явно описать, почему без неё нельзя (не воспроизводимо или требует секрета) и как гарантируется отсутствие «скрытого режима».

### Применение политики в репозитории

- Интеграционный скрипт всегда запускает полный стек без фильтрации сервисов.
- Тюнинг производительности (батчи импорта/экспорта, размеры пулов) выражен только через явно документированные переменные в соответствующих README (`backend/README.md`, `app/services/backup/README.md`).
- Временные «feature toggles» не добавляются; любые оптимизации фиксируются кодом по умолчанию.
