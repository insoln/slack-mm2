# Slack-MM2 Sync

Моно-репозиторий для приложения односторонней синхронизации данных Slack с Mattermost.

## Структура проекта

- `backend/` — Python FastAPI backend, реализующий API, обработку загрузки файлов и webhook.
- `frontend/` — React frontend, UI для загрузки файлов и мониторинга статуса.
  - Dev режим: исходники монтируются read-only; зависимости устанавливаются в эфемерную рабочую директорию контейнера при каждом старте (см. `frontend/README.md`).
- `infra/` — инфраструктура, манифесты Kubernetes, документация по деплою и настройке.

## Cursor instructions

- **Актуализация**: При любых изменениях в структуре или логике проекта README.md должен быть обновлён.

## Быстрый старт
Ниже краткий маршрут для локального dev-окружения (детали см. `backend/README.md`, `frontend/README.md`, `infra/README.md`).

1. Установите зависимости локально (опционально, для разработки вне Docker):
  ```bash
  pip install -r backend/requirements.txt
  npm -C frontend ci
  ```
2. Создайте `.env` для dev (токены фиктивны, используются только локально):
  ```bash
  cat > infra/.env <<EOF
  SLACK_VERIFICATION_TOKEN=test_token
  SLACK_BOT_TOKEN=test_bot_token
  SLACK_SIGNING_SECRET=test_signing_secret
  EOF
  ```
3. Поднимите всё окружение (всегда полный стек, без выборочного включения сервисов):
  ```bash
  docker compose -f infra/docker-compose.dev.yml up --build -d
  ```
4. Проверьте точки входа:
  - Backend: http://localhost:8000/healthcheck
  - Frontend: http://localhost:5173
  - Mattermost: http://localhost:8065
  - Test files (локальные вложения): http://localhost:9000
5. Загрузите тестовый архив Slack через UI или CLI: `curl -F file=@infra/test-data/slack-mini-backup.zip http://localhost:8000/upload`

### Мини-интеграционный прогон

Скрипт `scripts/run_mini_backup_integration.sh` выполняет детерминированную полную проверку импорта/экспорта на мини-наборе данных:
```
./scripts/run_mini_backup_integration.sh
```
Он гарантированно:
 - Поднимает полный docker-compose стек.
 - Убеждается в деплое/включении плагина Mattermost Importer.
 - Загружает мини-архив (`infra/test-data/slack-mini-backup.zip`).
 - Поллит `/jobs` до статуса success и проверяет итоговые счётчики.
 - Сканирует backend логи на ошибки и валидирует связывание admin пользователя.
 - Корректно гасит стек (даже при ошибке).

Используйте его локально и в CI для быстрой регрессии. Любые изменения структуры данных мини-набора должны сопровождаться обновлением ожидаемых метрик в самом скрипте.

### О сервисе test-files

В dev compose есть сервис `test-files` (порт 9000) — простой HTTP сервер, отдающий содержимое `infra/test-data/`. Мини-набор Slack указывает `url_private` вложений на `http://test-files:9000/...`, что устраняет сетевые задержки и делает проверку быстрой и повторяемой.

Политика: скрипты/документация **никогда** не подразумевают выборочное поднятие сервисов – всегда полный стек для исключения скрытых зависимостей.

## Важно
- Все пути к миграциям, SQL-скриптам и данным должны быть относительными (относительно текущего файла или рабочей директории), чтобы проект работал и в Docker, и при локальном запуске. 

## Политика ветвления (Branching Policy)
Все изменения вносятся ТОЛЬКО через отдельные ветки. Запрещено коммитить напрямую в `master`.

Шаги типового потока:
1. Обновить master: `git fetch origin && git checkout master && git pull --rebase`.
2. Создать ветку: `git checkout -b feature/<кратко>` (или `fix/`, `chore/`, `docs/`).
3. Вносить изменения — маленькие логически связанные коммиты, перед пушем запускать форматтеры и тесты.
4. Актуализировать ветку перед PR: `git fetch origin && git rebase origin/master`.
5. Пуш: `git push -u origin feature/<кратко>`.
6. Открыть Pull Request → дождаться CI → ревью → merge (squash или fast-forward).
7. Удалить ветку (локально и в origin).

Жёсткие правила:
- Никаких force push в `master`.
- `master` всегда в рабочем состоянии (тесты зелёные, миграции валидны).
- Хотфикс: `hotfix/<issue>` + PR, даже при срочности.
- Крупные рефакторинги — разбивать на серию PR.

Причины: чище история, меньше конфликтов, предсказуемый CI сигнал, возможность безопасного rebase.

## Важно для Docker Compose
- В сервисе backend не используется volume ../backend:/app, чтобы не перекрывать содержимое, скопированное в образ (особенно миграции). Это гарантирует, что проект работает и в Docker Compose, и при ручном запуске/сборке. 

## Структура автотестов (backend)

- `backend/tests/unit/` — юнит-тесты: отдельные функции, классы, утилиты, схемы. Все внешние зависимости мокируются.
- `backend/tests/integration/` — интеграционные тесты: тесты API, взаимодействия с БД, миграций, внешних сервисов.
- `backend/tests/conftest.py` — фикстуры для pytest (например, тестовый клиент FastAPI).

### Запуск тестов
- Юнит-тесты: `pytest backend/tests/unit`
- Интеграционные тесты: `pytest backend/tests/integration` 

## Интеграционные тесты Mattermost API
- Для тестов, обращающихся к Mattermost API, нужны переменные окружения:
  - `MATTERMOST_API_TOKEN` — access token пользователя Mattermost (например, admin)
  - `MATTERMOST_API_URL` — URL эндпоинта API (например, http://localhost:8065/api/v4/users/me)
- Для dev-окружения используйте токен и адрес из init-скрипта или создайте токен через mmctl.
- Для prod — используйте реальные значения из production Mattermost.
- Пример запуска:
  ```bash
  MATTERMOST_API_TOKEN=... MATTERMOST_API_URL=... pytest backend/tests/integration
  ```

## Pre-commit хуки

Чтобы автоматически проверять стиль и базовые ошибки перед коммитом, добавлен файл `.pre-commit-config.yaml`.

Установка и активация (один раз):
```bash
pip install -r backend/requirements.txt  # содержит pre-commit
pre-commit install
```

Что запускается при `git commit`:
- `black` — автоформатирование Python
- `end-of-file-fixer`, `trailing-whitespace`, `detect-private-key`, `check-added-large-files`
- Опциональный быстрый юнит-тест хук (`pytest-unit-fast`) — можно пропустить: `SKIP=pytest-unit-fast git commit -m "msg"`

Ручной прогон для всего репозитория (рекомендуется после больших refactor):
```bash
pre-commit run --all-files
```

Добавление нового hook:
1. Открыть `.pre-commit-config.yaml`
2. Добавить запись, указать `rev` (фиксированную версию)
3. `pre-commit autoupdate` (по желанию) и закоммитить изменения.

Если CI падает на format step — сначала локально запустить `pre-commit run --all-files` и повторить коммит.

## Логгирование
- Конфигурация логгирования вынесена в `app/logging_config.py`.
- Формат логов: время, уровень, имя логгера, сообщение.
- Для вывода своих сообщений используйте `from app.logging_config import backend_logger` и `backend_logger.info(...)`.
- Логгирование интегрировано с Uvicorn и поддерживает асинхронные задачи. 

## Запуск тестов: юнит vs интеграционные
- **Юнит-тесты** не требуют запуска внешних сервисов (БД, Mattermost, backend). Их можно запускать где угодно: локально, в CI, без Docker.
- **Интеграционные тесты** требуют, чтобы все внешние сервисы были доступны (backend, Mattermost, БД). Обычно их запускают из-под `docker compose up` или в CI, где все сервисы подняты синхронно.
- Для интеграционных тестов обязательно проверьте, что переменные окружения (`MATTERMOST_API_TOKEN`, `MATTERMOST_API_URL` и др.) указывают на правильные адреса сервисов. 

## Терминология
- **upload** — процесс загрузки файла (например, бэкапа Slack) с фронта на backend.
- **webhook** — приём обновления через вебхук (например, события из Slack в режиме реального времени).
- **parsing** — процедура чтения и разбора полученных данных (как из файла, так и из вебхука).
- **маппинг (mapping)** — одиночная распарсенная строка/объект, представляющая одну сущность (например, сообщение, пользователь, канал и т.д.).
- **импорт (import)** — процедура занесения маппинга в базу данных проекта.
- **экспорт (export)** — процедура отправки данных из маппинга в Mattermost (через API). 

## Политика использования переменных окружения

Мы намеренно минимизируем количество переменных окружения.

Принципы:
1. Только необходимая конфигурация среды: пути к сервисам (URL), токены доступа, размеры таймаутов/пулов соединений, параметры производительности, требуемые для развёртывания в разных окружениях (dev/stage/prod).
2. Никаких feature‑flags через env: функциональность приложения должна вести себя одинаково при одинаковой версии кода. Новые фичи включаются сразу (или за счёт явной логики версии данных / наличия сущностей), а не с помощью скрытых переключателей.
3. Повторяемость CI/Prod: всё, что влияет на ветвление логики, фиксируется в коде или конфигурационных файлах репозитория (migrations, manifests), а не в случайных переменных среды.
4. Допустимые исключения: секреты и параметры, которые невозможно хранить в Git (пароли, токены), а также значения, которые объективно различаются между инсталляциями (доменные имена, внешние URL). Они не должны менять поведение алгоритмов.
5. Если кажется, что нужна новая переменная окружения «чтобы быстро что‑то отключить/включить», сначала переосмысливаем архитектуру (можно ли сделать код идемпотентным / безопасным всегда) или фиксируем поведение через конфиг в репозитории.

Следствие: при ревью любой новой env переменной нужно явно описать, почему без неё нельзя (не воспроизводимо или требует секрета) и как гарантируется отсутствие «скрытого режима».

### Применение политики в репозитории

- Интеграционный скрипт всегда запускает полный стек без фильтрации сервисов.
- Тюнинг производительности (батчи импорта/экспорта, размеры пулов) выражен только через явно документированные переменные в соответствующих README (`backend/README.md`, `app/services/backup/README.md`).
- Временные «feature toggles» не добавляются; любые оптимизации фиксируются кодом по умолчанию.
